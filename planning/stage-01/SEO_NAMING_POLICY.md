# ARCHITEKTONICA — правила именования услуг для SEO / GEO / AEO

**Статус:** уточнение для утверждённой информационной архитектуры 01.11.2026; правила применяются к **разработке контента этапа 02**, а не означают завершённое семантическое исследование или утверждённые поисковые заголовки. Исследуем намерение и доступные данные спроса RU; отсутствие измерений отмечаем `unknown` с причиной и продолжаем подготовку чернового текста/SEO-пакета на явно обозначенных гипотезах. Не выдаём их за измеренную семантику; платные инструменты не являются обязательным условием. Источник неизменных 81 названий — [реестр услуг](../../references/project/services_catalogue.json), уникальные ID — [catalogue-map](catalogue-map.json).

## Главный принцип

**Не называть услугу по самому высокочастотному запросу автоматически.** Название должно быть профессионально точным, понятным покупателю услуги и соответствовать фактическому предложению. Высокая частотность сама по себе не доказывает коммерческое намерение, релевантность или достижимость результата. При выборе учитывать: задачу человека, сегмент B2B, язык профессионалов, конкурентную выдачу и доступность подтверждённого содержания.

Разделить три уровня:
1. `catalogue_name` — **точное исходное название** услуги и `service_id` из реестра. Не переписывается, не удаляется и не дублируется в процессе SEO.
2. `display_name` / `H1` — читабельное описание услуги на реальной странице; может быть редакционно уточнено по исследованному намерению, без искажения границ услуги.
3. `title`, `meta description`, `URL`, `summary`, `FAQ`, `internal anchors` — отдельные элементы SEO-пакета, формируемые для конкретной локали и страницы. Синонимы распределяются естественно, а не перечнем ключей.

Каждой **канонической** странице назначается одна главная задача/кластер поискового намерения. Раздел каталога и отдельная услуга должны дополнять, а не копировать друг друга. 81 запись не означает 81 SEO-лендинг. Готовность 13 кандидатов детальных страниц решается на этапе 02 после проверки объёма и отличимости контента.

## Режим исследования на этапе 02

Сформировать рабочую матрицу `service_id → исходное имя → вопрос клиента → коммерческий/информационный intent → RU поисковые формулировки → доказательство источника спроса → родительская страница → canonical URL → H1 → title → summary → FAQ → связанные кейсы/статьи → решение отдельная страница/секция`.

- Исследовать реальные формулировки для RU: Search Console (если появятся данные), Яндекс Вордстат, доступные инструменты Google и SERP-анализ на целевых рынках. Для международной EN-версии — отдельная семантика, не дословная калька.
- Различать частотность, намерение и конкурентность. Без свежих инструментальных данных **не помечать** запросы как высокочастотные и не выдумывать числа.
- Выбирать широкое понятное имя, если это тот же смысл, а точное отраслевое название оставлять там, где оно важно. Не делать ложных обещаний или более широких услуг ради ключа.
- Рядом с определением показать «что делаем / для кого / какой результат или артефакт согласовывается / как начинается работа / чем отличается от соседней услуги». Сведения об успешно выполненных проектах брать только из Case Studies, а не из предложения услуги.
- Экспертное объяснение может быть длинным и хорошо структурированным; отсутствие кейса не запрещает страницу предложения, но не даёт права выдумывать доказательства.
- Для семантического исследования учитывать реальные запросы и профессиональные синонимы (включая «ИИ» и «AI»), не выдавая гипотезу за измеренный спрос. В **публичных авторских текстах и H1** следовать [Language](../../references/project/05_Architektonica_Language.md): «AI», не «ИИ». Исходные названия каталога и дословные цитаты не переписывать.
- Для каждой потенциально похожей пары, особенно **«GEO» и «GEO — оптимизация для генеративного поиска»**, **«SEO» и «SEO и мультиязычное продвижение»**, фиксировать различие содержания/сценария и одну каноническую точку входа на общую задачу. Обе записи реестра сохраняются, но разные страницы только ради близких ключевых слов не создавать.
- Не повторять бренд, город, «заказать», «цена», «под ключ» в каждом заголовке без реального смысла, не публиковать масштабно однотипные тексты/doorway pages. Выразительная интонация ARCHITEKTONICA и читабельность важнее механической плотности ключей.

## Как это помогает AI-поиску (GEO/AEO)

Создавать единый проверяемый набор сведений: что предлагает компания, точное определение услуги, ограничения и стадии, специализация, доказательства, связанные материалы, устойчивые URL и каноническая связь «направление → услуга → кейс → статья». На страницах писать прямые ответы на реальные вопросы, представлять факты читаемым HTML и понятными заголовками, поддерживать доступность без принудительного WebGL.

JSON-LD размечает **только видимые и подтверждённые** данные (например, Organization на главной/About, BreadcrumbList и Article по применимости; JobPosting только на настоящей странице конкретной открытой вакансии). Разметка не заменяет контент, не гарантирует rich results и не является «секретом» попадания в ответ LLM. Для AI Overviews/AI Mode Google указывает, что действуют фундаментальные правила Search; специальный AI-файл или AI-schema не требуются.

**Задача Search Visibility на этапе 02:** предложить `query-intent → страница → название/H1/title → доказательства → internal links` после исследования, а главный исполнитель и редакторы делают готовый сильный текст. SEO не должно переписывать первичный каталог и художественную концепцию.
