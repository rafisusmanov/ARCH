# Search Visibility — исследование запросов и SERP (этап 02)

**Назначение.** Основанная на доказательствах поисковая семантика 17 направлений / 81 услуги, а также кейсов и статей. Не заменяет их названия из реестра и утверждённую информационную архитектуру. Используй вместе с основным [SKILL.md](../SKILL.md) и правилами [источников](EXTERNAL_SOURCES.md).

## 1. Единица работы — реальная потребность клиента

Входные данные: `service_id`, точное `catalogue_name`, его направление, предоставляемая услуга и границы, RU-аудитория/рынок, целевая бизнес-задача, связи с Case Studies и действующий статус страницы. Исходник названий — `references/project/services_catalogue.json`. При отсутствии поисковых метрик **не стопорить написание полезного содержания**: сначала собрать гипотезы и пометить отсутствие измерений.

Проверяй терминологию B2B-решений. «Проектирование архитектуры ИИ» не равно «внедрению готовой ИИ-системы». «Разработка сайта» не доказывает, что компания оказывает бухгалтерский аутсорсинг клиенту, для которого она сделала сайт.

## 2. Исследование и доказательства

1. Для каждой услуги определить **потребности клиента**: задачу, желаемый результат, опасения, уровень экспертизы, географию и предполагаемый этап принятия решения (знакомство / сравнение / готовность обратиться).
2. Сформировать seed-термины: официальное название, понятные профессиональные синонимы, конкретные типы результата, отраслевые слова и прямые вопросы. Не подменять смысл запросами с большей частотностью.
3. Разделить намерение на информационное, сравнительное/коммерческое, транзакционное и навигационное; фиксировать неоднозначность и множественный смысл (например, аббревиатура GEO).
4. Проверить **рынок и дату**: для первого RU-выпуска при наличии доступа отдельно Google и Яндекс; применимые средства — Яндекс Вордстат, Google Keyword Planner, Search Console (после получения данных), доступные инструменты выдачи. Автоподсказки, тематическая популярность и сторонние оценки — не фактическая поисковая частотность.
5. Для важных запросов рассмотреть текущую SERP: 5–10 результатов, типы лидирующих страниц, интент, локаль/язык, дата, desktop/mobile, вопросы из выдачи, блоки AI-поиска **если реально видны**. Скриншот/ответ сервиса не доказывает наличие каждого блока во всех регионах. Не переносить SERP Google на Яндекс без проверки.
6. Сопоставить конкуренцию и различимость содержания. Если похожие услуги решают один пользовательский запрос, рассматривать общий обзор/раздел или чётко различающиеся страницы, не плодить thin/doorway URLs.
7. Подготовить кластер запросов с **одним каноническим назначением** (страница направления, раздел услуги, отдельная страница только после содержательной проверки). План ссылки на будущий URL — не свидетельство существования страницы.

Для каждого **числового** поля сохранять значение, единицы, источник/ссылку, дату и период измерения, поисковую систему, локаль/регион и устройство при необходимости; статус `measured`, `provided`, `calculated`, `estimated`, `proxy` или `unknown`. Нет цифры → `unknown` с причиной, **никакого нуля, мнимого SEO Difficulty или Opportunity Score**. Не ставить «высокочастотный» без инструментального доказательства. Прокси данных Google Autocomplete/веб-поиска не превращать в месячную частотность.

## 3. Формат решения для каждой услуги

```text
service_id | catalogue_name | scope/confirmed offering
target_ru_audience | user_problem | intent | query_cluster
query_variant | search_engine | geo_locale | observation_date | evidence_ref | volume_state
proposed_page_type = direction_section / detail_candidate / approved_detail
canonical_content_id | proposed_url (не published) | related_case_ids | related_article_ids
H1_candidate | SEO_title_candidate | short_definition | practical_questions
open_evidence | risk_of_overlap | decision_and_reason | status
```

Для 81 услуг собрать **81 строку сохранённых идентификаторов**, не обязательно 81 SEO-посадочную страницу. В отдельном листе — группировка нескольких запросов к одной канонической странице. Для кейсов и статей сохранять конкретные `case_id` / `article_id`, стадию, доказанную роль компании и публикационный статус. Неподтверждённый кейс не становится SEO-доказательством.

## 4. Результат

- Структурированная семантическая матрица `service_id → intent → cluster → page/section`.
- Не более одной канонической страницы на **совпадающее** поисковое намерение; при разделении указывать содержательное различие, а не разные слова в title.
- Отдельный список `unknown` измерений и последующих источников; согласование приоритетов без выдуманной SEO-аналитики.
- Набор подтверждённых тем для блога, появляющихся из вопросов клиента, **не** автоматически опубликованных статей.
