# ARCHITEKTONICA — UI/UX Expert

## Цель
Создавать **премиальный, технологичный, иммерсивный корпоративный сайт ARCHITEKTONICA с выразительной пространственной глубиной**. Engine — приобретённый, но неидеальный шаблон, который существенно дорабатываем для настоящей иммерсивности, пространственной глубины и многослойности. Сохраняем сильное, а слабые элементы перерабатываем или заменяем. Его блоки подчиняются структуре сайта и окончательным текстам, а не наоборот.

## Приоритет источников

2. Авторские `architektonica-creative-director` и `architektonica-narrative-design`; канон текста и голоса — `../../../methods/site-voice-and-consistency.md`.
3. Методика UI UX Pro Max и каталог: `../../../third_party/ui-ux-pro-max/`; поисковая выдача — **гипотеза**, не дизайн-решение без контекста.
4. Экспертиза `emil-design-eng`, `animate`, `animation-performance`, `review-animations`, `mobile-native`, `break-ui`.

## Граница клиентского кабинета

**Решение владельца 02.11.2026:** на Stage 02 сейчас готовятся полноценная публичная страница и уместные блоки о кабинете в настоящем времени; после редакционного утверждения можно проектировать их публичный визуал с местами для реальных скриншотов, фото и видео. Кабинет может разрабатываться параллельно в отдельном Laravel-репозитории, но его завершение и запуск — после выпуска публичного сайта; внутренние экраны и backend не переносятся в WEB. Новый URL требует согласования IA; готовность Laravel не блокирует запуск WEB; не размещать неработающую ссылку входа. Основа: `../../../references/project/OWNER_DECISION_2026-11-02_CLIENT_WORKSPACE.md`. Голосовой AI-консультант — отдельная будущая задача.

## Архитектура контента (этап 01)
Перед проектированием навигации и страниц использовать [модель сущностей и связей](references/content-model.md): направления → услуги ↔ кейсы ↔ статьи, RU/EN, стабильные идентификаторы, URL и статусы публикации. Утверждённая информационная архитектура этапа 01 закреплена в `../../../planning/stage-01/IA_PROPOSAL.md`; эта вспомогательная модель описывает сущности и связи, но не заменяет утверждённую IA, не является готовой CMS и не означает автоматическое создание 81 страницы. Читать применимые авторские навыки и валидировать каталог 17/81.

## Протокол
1. Сначала определить карту сайта и сценарии читателя, затем законченные тексты и структуру статей/услуг; только после этого проектировать блоки, сохраняя, перерабатывая, расширяя или заменяя элементы Engine по смыслу. Перед работой прочитать применимые `SKILL.md` по маршруту в `../../../methods/engine-template-adaptation.md`.
2. Если для новой сцены нужна референсная база, из корня репозитория выполнить `python3 third_party/ui-ux-pro-max/scripts/search.py "premium immersive multidisciplinary corporate portfolio" --design-system -p ARCHITEKTONICA`. При работе из другого каталога использовать абсолютный путь к скрипту. Выдача — гипотеза; не применять палитру/шрифт/паттерн автоматически. Сохранение `--persist` допустимо в явно выбранный рабочий каталог; `--force` не должен перезаписывать утверждённые решения без согласования.
3. Исследовать нужный домен точечно: `--domain style`, `ux`, `landing`, `gsap`, `typography`; для конкретной технологии — только поддерживаемый `--stack`. Частично поставляемые данные не выдавать за весь upstream; CI проверяет доступность заявленных каталогов.
4. Для выбора новой визуальной концепции предложить различающиеся направления и рекомендовать вариант. Для точечной правки или уже утверждённой концепции развивать выбранное решение без обязательной генерации альтернатив. Сцены опирать на утверждённое содержание и задачу страницы. Конкретный кейс использовать только если выбран для этой страницы и подтверждён; главная не требует портфолио. Роли источников: `../../../methods/editorial-source-boundaries.md`.
5. Проектировать **ощутимую пространственную глубину**: передний, средний и дальний планы, масштаб, перспективу, перекрытия, светотень и смысловой ритм. Параллакс и реакции на курсор — опциональны; `z-index` задаёт порядок наложения, не 3D-перспективу. Для 3D применять CSS `perspective`/`transform` либо WebGL/Three.js только по обоснованной задаче. Не путать визуальную глубину с загромождением.
6. Создавать desktop/tablet/mobile и no-motion концепции одновременно. Проверять клавиатуру, touch, фокус, контраст, читабельность, загрузку медиаресурсов и энергозатраты на смартфонах.
7. Для реализации motion читать `animate`, для диагностики — `animation-performance`, для интерфейса — `emil-design-eng`, для пограничных состояний — `break-ui`. `review-animations` и `prototype` имеют `disable-model-invocation: true`: открывать для применения только по явному запросу пользователя на соответствующий навык. Общий запрос на качество не отменяет этот флаг. Проектные адаптации внешних правил — в `../../../methods/engine-template-adaptation.md`.
8. Публичный сайт сохраняет PHP/HTML/CSS/JavaScript, GSAP/ScrollTrigger и Lenis. Изменение стека требует технического обоснования и отдельного разрешения владельца; примеры React/Next/Tailwind в справочниках такого разрешения не дают.
9. Следовать этапам утверждённого плана версии 2.0. Внутренний контракт блока: **Задача читателя → Контент → Композиция → Решение по Engine → Пространственная глубина / motion → Использованные навыки → Проверки качества**. Техническую проверку вести по мере реализации, не начинать с отвлечённого аудита Engine.
10. Документировать решения и альтернативы, подтверждать результаты работающей демонстрацией, а не только описанием.
