# ARCHITEKTONICA — вспомогательная модель контента и связей

Это **вспомогательная модель сущностей** для подготовки содержания и последующей реализации, а не готовая БД и не самостоятельное решение об архитектуре сайта. Утверждённая информационная архитектура этапа 01 и URL-контракт закреплены в [IA_PROPOSAL.md](../../../../planning/stage-01/IA_PROPOSAL.md) и [JOURNEYS_AND_URLS.md](../../../../planning/stage-01/JOURNEYS_AND_URLS.md). Исходные факты — Fact Bank, 17 направлений / 81 услуга и проверенные Case Studies. Различать `content ID` (неизменный), публичный slug (изменяемый до утверждения маршрута либо по отдельному решению владельца) и локализованную страницу. Уже утверждённые URL и назначения услуг из `catalogue-map.json` не менять при подготовке текстов и SEO-пакетов этапа 02.

| Сущность | Минимальные поля | Связи |
|---|---|---|
| Direction (направление) | `id`, название из реестра, `status`, `order` | основные/дополнительные услуги |
| Service (услуга) | `id`, оригинальное название, `primary_direction_id`, краткое/полное содержание, `detail_page`, `status` | одна основная категория; несколько тематических; связанные кейсы/статьи |
| Case (кейс) | `id`, проверенный title, роль компании, `stage`, права на публикацию, медиа, `status` | услуги/направления, статьи |
| Article (статья) | `id`, заголовок, введение, редакционные блоки, рубрика, автор/дата если подтверждены, `status` | услуги, направления, кейсы, другие статьи |
| ContentPage | `id`, `page_type`, блоки, `status` | один или несколько основных материалов |
| Translation/Locale | `entity_type`, `entity_id`, `locale`, `slug`, `title`, `summary`, `body/blocks`, `translation_status` | к каждому типу опубликованной страницы |

Статусы: `draft` → `in_review` → `approved` → `published` → `archived`; значения для будущей реализации согласовать. Владелец выбрал управление материалами и статьями через управляющую часть `rafisusmanov/Arhitektonica`; эта модель не является готовой БД, реализованной интеграцией или разрешением создавать вторую CMS в WEB. Срок подключения и технический контракт согласуются отдельно. Не публиковать черновики. Translation status хранить отдельно: первый выпуск — RU, EN — отдельный согласованный выпуск; непереведённое содержание не маркировать как готовое EN.

## Инварианты
1. Владелец утвердил 10.11.2026 **17 направлений / 77 уникальных публичных услуг / 6 групп**, см. [публичный манифест](../../../../planning/stage-02/public-service-catalogue.json). Исторические 81 ID сохранены отдельно для обратной совместимости, см. Stage 01. Навигационные группы не меняют состав каталога.
2. У каждой услуги один первичный устойчивый `direction_id`, дополнительные связи не создают дублей услуг; решение о детальной странице отдельно. Нельзя автоматически генерировать 81 тонкую страницу.
3. Case ссылается только на подтверждённые факты и стадию (концепция, архитектура, прототип, пилот, внедрение), не создавать неподтверждённые результаты и цифры.
4. Article и Case могут связываться с несколькими услугами/направлениями; связи двунаправленно проверяются, карточки без опубликованной цели не появляются.
5. `entity_id + locale` однозначно определяет локализованную версию; один canonical URL на опубликованную локаль, hreflang только для существующих взаимных языковых версий. Утверждённая URL-стратегия: RU в корне `/`, будущая EN-версия под `/en`; EN-страницы и hreflang не публиковать до готовности соответствующего контента.
6. Если перевод, автор, дата, фото, кейс или правовой статус неизвестны — не выдумывать данные и не создавать публичную заглушку.
7. Контентная модель и структура редакционных блоков определяются содержанием. Engine используется как библиотека UI-решений, не как ограничение их числа.

## Перед проектированием страницы
Сформировать компактную таблицу `entity ID → page type → locale → slug → source → publication status → linked services/cases/articles → CTA`. Отразить направления входа, breadcrumbs и связи. Валидировать URL на дубли и циклы, статусы на доступность, связность «услуга → кейс → статья». На странице читатель видит не схему БД, а ясную историю с возможностью углубиться.

Источники для профессионального подхода: [site-architecture](https://github.com/coreyhaines31/marketingskills/tree/main/skills/site-architecture), [domain-modeling](https://github.com/mattpocock/skills/tree/main/skills/engineering/domain-modeling). Это **референсы**, не устанавливаемые дополнительные навыки.
