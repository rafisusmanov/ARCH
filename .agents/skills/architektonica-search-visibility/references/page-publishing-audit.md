# Search Visibility — SEO-пакет страницы и доказательный аудит

Режимы по этапам: **02 — проектирование title/H1, поисковых вопросов и статуса**, **05 — техническое внедрение в PHP/WEB**, **06–07 — проверка на реально работающей странице**. Не выдавать концептуальный checklist за пройденное тестирование. Используй совместно Website QA (`skills/architektonica-website-qa/SKILL.md`) по настоящему preview после реализации.

## A. SEO-пакет на этапе 02

Для одной страницы утверждённой IA подготовить **черновой SEO-пакет вместе с текстом, до утверждения контента**. Для кандидата отдельной страницы сначала проверить самостоятельность содержания; подготовка пакета не разрешает публикацию:
- `content_id`, `page_type`, `locale`, `publication_status`, `approved_source`, реальное `user_intent`.
- `URL` как утверждённый/предложенный, `H1`, 1–3 варианта `title` и `meta description` **без обязательной длины по символам**; главное — точность, ясность и отсутствие однотипных дублей. Title может быть поисково прямым, а H1 — выразительным при понятном подзаголовке.
- Структуру H2/H3 под реальный текст, открывающий ответ на запрос без Keyword Stuffing; вопросы и FAQ только по содержанию.
- `links`: целевые content_id, осмысленные якорные тексты и статус цели. В проекте допустимы планируемые связи с `draft` / `not_approved`, явно без статуса рабочей ссылки; в опубликованном HTML — только реально опубликованные цели. Не создавать публичную ссылку на несуществующую EN-страницу.
- `schema_candidates`: `Organization`, `BreadcrumbList`, `Article`, `JobPosting` **только по типу и подтверждённым видимым фактам**; это предложение, не готовый JSON-LD.
- Бренд ARCHITEKTONICA, стадию и роль в кейсах брать из первичных материалов. Не придумывать price, aggregateRating, Review, author, date, LocalBusiness-адрес.

Для вакансий: `/careers` — независимый пункт главного меню и страница списка; `JobPosting` **только на странице конкретной реальной открытой вакансии**, не на списке.

## B. Техническая передача в WEB (этап 05)

В рамках PHP/Beget проекта отдельно проверить и внедрить:
- Уникальные URL/title/canonical; корректные HTTP 301/404, `robots.txt`, `sitemap.xml` и статусы индексации **после подтверждения контента**. Preview, демо-кейсы, неопубликованные и будущие EN-страницы не индексируются.
- HTML основного текста и ключевых ссылок доступен без JS (GSAP/Three/Webflow не должны быть единственным источником содержания).
- Реально опубликованным RU/EN-парам — согласованные взаимные `hreflang`. EN не дублировать русским placeholder.
- JSON-LD должен соответствовать **видимому** содержанию; валидировать Schema.org Validator и, для поддерживаемых типов, Google Rich Results Test. Не обещать rich snippet за факт наличия JSON-LD.
- Перекрёстная проверка raw HTML и rendered DOM: если не видно разметку в raw, не делать вывод «нет schema» без rendered-анализа. Но для критического текста предпочтителен серверный HTML.
- Разметка FAQPage и HowTo может быть семантической по применимости, но не обещать расширенные результаты Google: требования и поддержка меняются, перепроверять официальную документацию на момент реализации.
- Провести по опубликованным URL мобильный и браузерный аудит; Lighthouse лабораторный, CrUX/полевые CWV отдельные; считать реальные замеры, не придумывать улучшения.

## C. Адаптированный чек-лист аудита SNLabat

Не требовать вопроса «Quick или Full?» при каждом обращении и не генерировать DOCX/PDF автоматически. Формат выводится из задачи.

| Плоскость | Фактическая проверка | Доказательство |
|---|---|---|
| SEO — HTML | Title, description, H1/H2, canonical, media alt, индексируемость, ссылки | URL + дата + raw/rendered HTML, найденные значения |
| SEO — архитектура | 17/81, canonical intent, URL и связность, редиректы, дубль контента | sitemap, mapping IDs и crawl результатов |
| GEO — проверяемые сущности | Компания, услуги, кейсы, роль/стадия, авторы и источники | Fact Bank / Case Studies / опубликованный HTML |
| GEO — пригодность ответа | Точные определения, контекст, источники, доступность текста без обязательной анимации | конкретный фрагмент и запрос, скрин/HTML |
| AEO — ответ на вопрос | Реальные вопросы посетителя, прямой ответ, полезный список/таблица где уместны | URL, вопрос, ответ и наблюдаемый SERP при наличии |
| Техническое | robots, sitemap, schema, 301/404, hreflang, CWV, mobile | live/staging измерения и валидаторы |
| Измерение | конверсии по серверно подтверждённым заявкам и реферальный трафик | approved analytics contract, event source, период |

Каждое замечание имеет `scope URL | locale | source | observation date | PASS/FAIL/UNKNOWN/NOT RUN | severity | fix | recheck`. Приоритет P0 — уязвимость/потеря лида/недопустимая публикация или блокирующая индексация критического релизного пути; P1 — значимые ошибки обнаруживаемости/контента; P2 — локальная доработка. **Баллы 1–10 для SEO/GEO/AEO не использовать** без независимой калибровки — они не доказывают видимость.

### Quick vs Full

- **Quick**: конкретная страница/проблема, несколько связанных URL — короткий список наблюдаемых дефектов и приоритетов.
- **Full**: согласованный набор публичных URL/типов страниц с явной матрицей покрытия. «Full» не значит безлимитный crawl всех ссылок.
- При недоступном URL, отсутствии среды браузера или поисковых данных честно отметить `NOT RUN`; не заявлять, что title отсутствует на странице, которую не удалось прочитать.
- Сравнение до/после только при сохранённом базовом состоянии и одинаковой среде. `GEO readiness` не равно доказанное цитирование.
