# Search Visibility — структура поиска, каноникализация и внутренние связи

Использовать **только в рамках утверждённого sitemap** и статусов публикации. Это уточнение к архитектуре, не разрешение перекроить 17 направлений / 81 услугу и не замена согласованию изменений владельцем.

## Два режима

### Режим A: намерение → посадочная страница (этапы 01–02)

1. Сверить все 17 направлений и 81 услугу с исходным реестром, не создавать дубликаты и не уменьшать объём. Обзорные группы — дополнительный навигационный слой.
2. Назначить каждой семантической группе ключевой `content_id` и `page_type`: каталог, направление, полноценный раздел услуги, индивидуальная услуга-кандидат, кейс, статья, вакансии.
3. Для пары похожих услуг проверить **разные намерения** и отсутствие каннибализации. Пример: «GEO» vs «GEO — оптимизация для генеративного поиска»; две записи каталога остаются, но два URL только при предметном различии.
4. Отдельный URL разрешён после редакционной проверки глубины, уникальности задачи и реальной пользы. Иначе полноценный раздел с якорем на странице направления.
5. RU впервые — корневой адрес; будущая EN-версия — собственный `/en/...` только после подтверждённого перевода. `hreflang` только для реально опубликованных взаимных версий, `canonical` только для существующих страниц.
6. Включить самостоятельные «Вакансии» в основную навигацию: `/careers`, индивидуальные `/careers/<vacancy-slug>` для подтверждённых открытых позиций. Не прятать под `/about`; не публиковать пустые вакансии.

### Режим B: граф ссылок и устранение сирот (этапы 02/05/06)

Собрать таблицу `source_content_id | source_url | destination_content_id | destination_url | anchor | contextual_reason | status`.
Проверять:
- Главная → тематический вход → направление → конкретная услуга / кейс / статья → контакт.
- Обратную связь опубликованного кейса с услугой только при подтверждённом вкладе; не приписывать проекты компании по сходству отрасли.
- Статья ↔ вопрос клиента ↔ подходящие услуги; кейсы только при подтверждённой релевантности. Связи с Case/Article необязательны для каждой услуги; путь к направлению и контакту сохраняется без них. Не создавать механический блок «три статьи» из Engine.
- Отсутствие orphan pages, ссылок на `draft` или `not_approved`, цепочек редиректов и неработающих якорей.
- Навигацию при keyboard/no-JS/reduced motion; ссылки и основной текст доступны в серверном HTML PHP, не только после работы GSAP.
- Для миграции `/project` → `/projects` предусмотреть карту существующих публичных адресов и индивидуальных 301 **только при изменении роутера WEB**, не создавать их в Creative.

Данные crawler/linkgraph — свидетельство только наблюдённой среды: фиксировать commit, URL preview/production, дату, локаль, статус индексации. До живого обхода приводить **план связей**, а не «отчёт о проверенных сиротах». Для неточных данных ставить NOT RUN.

## Выход

Предложенные `content_id → URL → intent`, карта межстраничных ссылок, список пересечений и приоритетов; для опубликованного сайта — конкретные `source URL → target URL → anchor`, воспроизводимые дефекты и проверки. Метрика «structure score /100» из внешнего источника необязательна и не является признаком одобрения владельцем.
