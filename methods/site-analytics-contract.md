# ARCHITEKTONICA — контракт измерения сайта (этапы 05–07)

**Статус:** спецификация для будущей реализации в ARCHITEKTONICA-WEB; не подключённая аналитика. Сначала утвердить систему аналитики, согласие и политику конфиденциальности, затем реализовывать события. Не отправлять персональные данные из формы в веб-аналитику.

## События и бизнес-смысл

| Событие | Условие | Примечание |
|---|---|---|
| `service_view` | Просмотр реальной опубликованной услуги | Только существующий service_id; не использовать автоматический счётчик каждой анимации |
| `case_open` | Реальный переход на опубликованный кейс | Допускается связанность с service_id |
| `article_open` | Реальный переход к опубликованной статье | Не считать автопоявление блока за клик |
| `contact_cta_click` | Явное действие по переходу к связи | Событие интереса, **не заявка** |
| `contact_form_start` | Первое осмысленное взаимодействие с формой | Не считывать значения полей |
| `contact_submit_attempt` | Разрешённая активная форма: попытка отправки | Исключить preview-отказы как конверсию |
| `lead_confirmed` | **Сервер** успешно принял и надёжно сохранил/передал обращение, зафиксирована единая ID заявки | **Единственная основная конверсия.** Не считать клик или HTTP 200 HTML за успешную заявку |

## Безопасные параметры
Допустимые по необходимости: `event_name`, `event_id`, `page_type`, `locale` (`ru`/`en`), `service_id` (из реестра), `source_section`, `client_build`, технический `form_id`. Без имён, телефонов, email, адресов, текста сообщений, IP, уникальных пользовательских токенов, идентификаторов сессии/заявки в сторонней аналитике или произвольных значений URL. Фактический набор зависит от согласия/правовой оценки.

## Доставка и защита от двойного подсчёта
- Одно подтверждённое обращение = **один** внутренний `lead_id` и максимум **одно** `lead_confirmed`; механизм идемпотентности — серверная проверка повторов/ретраев. Идентификатор обращения **не экспортировать** в стороннюю аналитику.
- Подтверждение приходит только от доверенного backend после успешной обработки; frontend не вправе генерировать `lead_confirmed` по нажатию кнопки.
- На preview/CI тестовые заявки маркировать и **исключать из production-отчётов**. Аналитику реальных посетителей preview отключить.
- Проверять с согласованными настройками consent, применимыми требованиями конфиденциальности и документированной политикой хранения. Если согласие не дано — не включать необязательное отслеживание.
- Наблюдать ошибки доставки отдельно, не маскируя потерянные заявки «успешной» конверсией.

## Приёмочные проверки после внедрения (WEB)
1. Вывести тестовую заявку через форму при включённой серверной интеграции; удостовериться в фактической доставке/сохранении и **единственном** событии `lead_confirmed`.
2. Повторный POST/refresh/двойной клик/сетевой retry не создаёт дубликат конверсии.
3. Отказ валидации, блокировка антиспамом, истечение сессии, ошибка сервера и отключённая preview-форма **не** создают `lead_confirmed`.
4. Проверить события `service_view`, `case_open`, `article_open`, `contact_cta_click` на одной русской и одной английской странице (после публикации перевода).
5. С выключенным consent проверить отсутствие необязательных событий/запросов. Исследовать сетевые payload и удостовериться, что персональных данных там нет.
6. Проверить backend-логи ошибок и журнал попыток доставки с ограничением доступа, без утечки содержимого обращения в публичные логи.
