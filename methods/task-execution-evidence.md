# ARCHITEKTONICA · Исполнение задач и доказательства работы навыков

**Канонический реестр:** [`task-skill-matrix.yaml`](task-skill-matrix.yaml). Он дополняет утверждённый план v2, но не переписывает его и не меняет решение владельца о единственной активной задаче. В случае противоречия применяются приоритеты `AGENTS.md` и текущие решения владельца; ошибку матрицы нужно исправлять отдельным PR, а не игнорировать молча.

## Четыре уровня контроля

1. **Обнаружение:** `python3 scripts/skill_catalog.py --json` и `python3 scripts/verify_package.py` проверяют реальное существование навыков, правильность YAML, зеркал, рецептов, ссылок и согласованного снимка плана. Это не активация навыков.
2. **Маршрутизация:** `python3 scripts/task_skill_router.py validate` сверяет все семь этапов, 20 обнаруженных навыков, 24 типовых задачи, источники, условия, явные режимы и контрольные сценарии. Если задача отсутствует, **не выбирать навыки наугад**: `BLOCK_AND_ROUTE_FOR_REVIEW`; добавить покрытие через отдельный PR. При появлении нового навыка CI потребует явного включения в маршрутизацию.
3. **Следы фактического обращения к источникам:** `python3 scripts/task_skill_router.py plan --task content.services-overview` формирует обязательный список читаемых `SKILL.md` и источников. После работы передайте экспорт **реальных tool-call событий**, а не рассказ агента о прочитанном, команде `audit --trace <path.json>`. Требуются пути, SHA-256 и идентификатор фактического вызова инструмента. Пропуск, подмена hash или `self_report` возвращает FAIL. **Внешнее происхождение JSON логом не аутентифицируется криптографически**: даже при полном покрытии статус `TRACE_COVERAGE_UNAUTHENTICATED`, не подтверждение понимания файла. В отсутствие экспорта оригинальных событий – `NOT VERIFIED`, не PASS.
4. **Качество результата:** отдельно проверять задания из `tests/fixtures/skill-evaluation-cases.json`, реальные outputs, source trace, критерии конкретной задачи, факты, кодовые/браузерные измерения и решение владельца. Рецензент не должен оценивать только формальную инструкцию; авторский самоотчёт не равен независимой проверке. Реальные испытания модели и review фиксируются `PASS/FAIL/NOT RUN` со ссылкой на артефакты, SHA, среду и исполнителя проверки.

## Пример вызова для текущей задачи

```bash
python3 scripts/task_skill_router.py validate
python3 scripts/task_skill_router.py plan --task content.services-overview --condition new_concept
python3 scripts/task_skill_router.py audit --trace path/to/exported-tool-log.json
python3 -m unittest discover -s tests -v
```

Условие `--condition` добавляет конкретный условный навык **только когда условие действительно установлено**. Отсутствие условия не разрешает пропуск обязательных навыков. Для задач `design.variants` и `motion.review-explicit` требуется явный запрос пользователя, например `--explicit prototype` или `--explicit review-animations`. Никакая таблица этапа не даёт права запустить их автоматически.

Минимальный пример **структуры** одного события (демонстрация формата, не результат реального прогона):

```json
{
  "task_id": "content.services-overview",
  "conditions": [],
  "explicit_user_request": [],
  "events": [
    {
      "type": "file_read",
      "origin": "tool_log",
      "tool_call_id": "ACTUAL-EXPORTED-CALL-ID",
      "path": "AGENTS.md",
      "sha256": "ACTUAL-SHA256-FROM-READ-SNAPSHOT"
    }
  ]
}
```

При реальном аудите один такой event недостаточен: нужны **все** обязательные источники и `SKILL.md`; файл читается из того же commit, что проверяемые SHA-256. Статический `verify_package.py` не создаёт такие журналы.

## Границы автоматизации и приёмки

- Матрица описывает **типовую задачу**, а не выполняет её. Каждое фактическое задание должно соответствовать ровно одному `task_id` и текущему owner-gate. Задачи, отсутствующие в матрице, сначала классифицируются/добавляются, не проталкиваются мимо проверки.
- Реестр перечисляет обязательные файлы. Если дополнительный материал становится необходимым по контексту, агент обязан открыть и его; статический список не является разрешением игнорировать реальные новые факты.
- Тест на чтение файла не доказывает соблюдение правил, качество копирайтинга, безопасность PHP или качество motion. Для этого требуются поведенческие испытания и предметная экспертиза.
- На STAGE 02 любые редакционные версии показывать владельцу в чате до записи в ARCH. WEB остаётся read-only до отдельного разрешения. Stage 03–07 не считаются автоматически разрешёнными или завершёнными.
- Утверждённый `ARCHITEKTONICA_SITE_PLAN_V2.md` содержит исторические обозначения: `Copy Studio` означает роль главного автора, а не существующий skill; публичный каталог сегодня `6/17/87`, `81` – только сохранение старых ID; отдельный `/process` отменён. `prototype` и `review-animations` – explicit-only независимо от списка навыков старого плана.
- UI/UX Pro Max – `third_party/ui-ux-pro-max/SKILL.md` и собственные CLI-данные, подключается через `architektonica-ui-ux-expert`, не отдельный 21-й автоактивируемый навык. Его присутствие и файлы проверяются пакетом.
- Оценка независимого поведения **NOT RUN**, пока не сохранены реальные ответы модели, инструментальные журналы и внешняя экспертная рецензия; зелёный CI этого статуса не меняет.

## Ключевое правило

**Если обязательный навык не открыт или нет проверяемого доказательства чтения, задача не может считаться проверенной.** Если качество материала не подтверждено, нельзя подменять проверку утверждением «все навыки применены».
