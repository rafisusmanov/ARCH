# ARCHITEKTONICA — протокол экспертного агента

**Назначение:** операционный порядок для Codex/AI при работе над сайтом. Канон решений — [AGENTS](../AGENTS.md); неизменяемая последовательность и точки согласования — [план v2](../references/project/ARCHITEKTONICA_SITE_PLAN_V2.md); [карта навыков](engine-template-adaptation.md) — источник маршрутизации. Этот документ **не новый этап и не замена плану**.

## Актуальные границы проекта

На Stage 02 сейчас готовить полноценные публичные тексты и блоки о кабинете в настоящем времени, включая места для будущих медиа; разработка Laravel-кабинета в отдельном репозитории может идти параллельно, но его завершение и запуск — после выпуска публичного сайта. Внутренние экраны и backend не переносить в WEB. Голосовой AI-консультант также откладывается до отдельного следующего цикла, без интерфейса в текущем сайте. При этом Engine — неидеальная стартовая основа, требующая существенного изменения для глубины, многослойности и иммерсивности.

Для каждой страницы достаточно одного ведущего автора, применимых фактологических/редакторских проверок и готового результата; **не требовать утверждения внутренних промежуточных решений**. Публикационные варианты сначала показать в чате; запись конкретного материала в GitHub разрешена только после явного согласования владельцем его точного объёма. После сброса 03.11.2026 старые частичные согласования не действуют; состояние брать из [WORK_MAP](../planning/stage-02/WORK_MAP.md). Владелец принимает цельный корпус Stage 02 согласно плану v2. Работа Stage 03–04 может предварительно исследоваться при прямом поручении, но это не означает формального закрытия Stage 02 и не даёт разрешения на публикацию. ## Обязательный цикл на каждую существенную задачу

1. **Ориентация.** Прочитать AGENTS и план v2; определить текущий этап 01–07 по фактически утверждённым результатам, а не по предполагаемой готовности. Если статуса утверждения не видно, считать его неподтверждённым.
2. **Декомпозиция.** Определить конкретный deliverable текущего этапа, аудиторию и ожидаемую пользу посетителю, исходные данные, зависимости, критерии приёмки. Зафиксировать в задаче/PR, без дополнительной бюрократии.
3. **Маршрутизация.** Запустить `python3 scripts/skill_catalog.py --json` (либо прочитать метаданные реальных skill-директорий при отсутствии shell). Выбрать **релевантные** навыки по описанию и [карте](engine-template-adaptation.md). Прочитать соответствующие SKILL.md целиком и связанные рецепты; `disable-model-invocation: true` не обходить.
4. **Источник и границы.** Проверить назначение источников по [редакционному контракту](editorial-source-boundaries.md): Brand Core – идентичность, Services – предложение, IA – маршруты, Fact Bank – факты; Case Studies – только релевантные выбранные работы. Сверить каталог 17/81, статусы и решения владельца. Если задача WEB — сверить актуальную ветку WEB и реальные маршруты, не приписывать отсутствующие функции.
5. **Исполнение.** Выполнить именно заявленный результат: одна карточка, шесть групп и CTA не равны полной странице каталога. Сверять назначение каждого WEB-блока и обязательные маршруты IA по [полностраничному контракту](stage-02-full-page-contract.md). Сильные решения Engine сохранять и развивать, слабые перерабатывать или заменять под утверждённую структуру и текст; объём доработки определяется требуемой глубиной и качеством. Внутренний контракт блока: задача читателя → текст → композиция → решение Engine → глубина/motion → использованные навыки → проверки.
6. **Независимая проверка.** Для страниц – сверить полноту всей композиции относительно WEB, IA и согласованных референсов, не только отдельные абзацы. Смысловой результат `FAIL`, если отсутствуют необходимые секции или связи, даже при зелёном CI.  Сравнить результат с исходными требованиями, всеми затронутыми методиками и условиями приёмки. Проверить факты и статус реализации. Для кода — применимые lint/tests/CI; для интерфейса — реальный preview и Website QA; для текста — редакционная и фактологическая проверка. После исправлений перепроверить. Отмечать PASS / FAIL / NOT RUN, не заменяя фактическое выполнение рекомендацией.
7. **Отчёт и gate.** Показать готовый результат, кратко указать открытые навыки/источники, реальные проверки и ограничения. Представить владельцу на утверждение **результат этапа**; переходить к следующему этапу только после явного утверждения его результата, кроме подготовительной параллельной работы без подмены gate.

## Текущее состояние этапов — правило фиксации
Не вести «утверждённый» прогресс только в тексте AI-ответа. Для каждого этапа хранить ссылку на утверждённый результат и подтверждение решения владельца в обычной задаче/PR или проектном реестре. Если нет ссылки — `approval: unverified`, следующий этап нельзя объявлять утверждённым. **Утверждение всей дорожной карты не означает утверждения результатов 01–07.** Запрещено самовольно менять этот документ на список «все готово».

Рекомендованные поля записи (в существующей задаче): `stage`, `deliverable`, `source_commit`, `skills_read`, `evidence`, `checks`, `owner_approval_ref`, `open_issues`, `next_action`. Не включать персональные данные из форм.

Малое безопасное исправление в рамках прямого поручения не требует повторного утверждения этапа; оно не переводит весь этап в завершённый. Разрешённое исследование будущей сцены обозначать как подготовку с `approval: unverified`, пока нет принятой архитектуры и содержания.

## Передача утверждённого результата Creative → WEB

Текущее решение владельца 10.11.2026: до отдельного разрешения сайт `ARCHITEKTONICA-WEB` полностью **read-only**; утверждение методики/текста не даёт разрешения менять WEB. При отдельно разрешённой будущей реализации в существующем WEB Issue/PR указать commit Creative, точные исходные материалы и их `owner_approval_ref`, целевой commit WEB, сопоставление content ID/локали/URL/блока и изменяемые файлы. Перед реализацией сверить актуальность обеих версий. Пока у материала нет стабильного ID, обозначить его как предложенный и согласовать на этапе 01, не считать номер строки каталога идентификатором.

При входе в WEB сверить его AGENTS и SITE_ROADMAP с утверждённым планом v2 Creative: совпадение номера этапа не означает совпадения содержания. Старый WEB-план не должен возвращать отдельный стартовый аудит или переносить содержание после дизайна. При расхождении зафиксировать его в задаче; синхронизировать WEB-документы отдельным разрешённым изменением до зависимой реализации, сохраняя канон v2. Read-only поручение на WEB не разрешает такую правку само по себе.

После реализации сравнить текст, факты, стадии проектов и состав услуг с утверждённым источником; адаптация разметки не разрешает редакционную замену. Изменение смысла или утверждённой навигации представить отдельным решением владельцу. В PR приложить diff и применимые проверки, сохраняя NOT RUN для непроверенных браузеров/устройств. Эти поля не требуют нового реестра или конкурирующей дорожной карты.

## Принцип автоматических проверок

CI блокирует только механически проверяемые нарушения: расхождение утверждённых ID/URL и каталога 17/81, потерю фактических источников, сломанные пути и зеркала навыков, опасные режимы активации, ошибки кода и безопасности. **Не вводить искусственные стоп-факторы** из-за переформулировки русских инструкций, количества добавленных корректных навыков, числа учебных сценариев, количества подключённых вспомогательных ролей или необходимости промежуточного отчёта. Навык выбирается по задаче, а не по квоте; утверждённый Stage 01 не переоткрывается при написании Stage 02. Проверка литературного качества, корректности обещаний и семантических противоречий документов проводится на реальном материале с участием человека; успешный CI никогда не означает редакционную приёмку или доказанное поведение агента.

## Правила качественной работы
- Перепроверять после каждого значимого исправления, перед PR и перед представлением результата владельцу; при новых источниках данных — повторно проверять затронутую часть.
- Не выдавать наличие инструкции за выполнение теста, синтетический screenshot за браузерный QA и локальный smoke за Beget production.
- Признавать блокирующие факты, неизвестные значения и отсутствие утверждения; не выдумывать, чтобы скрыть пробел.
- Не тормозить малую задачу полным аудитом всего репозитория. Проверки пропорциональны риску и изменениям.
- Реальные исправления через отдельные feature-ветки и PR, без прямой записи в main и слияния без решения владельца.

## Проверка новых решений владельца между репозиториями

При новом решении владельца сверять одновременно активные `skills/*/SKILL.md`, зеркала `.agents/skills`, инструкции `AGENTS.md` и `README.md` в Creative и границы смежных WEB/Laravel-проектов. Решение о кабинете от 02.11.2026 [зафиксировано отдельно](../references/project/OWNER_DECISION_2026-11-02_CLIENT_WORKSPACE.md): Stage 02 пишет текст сейчас в настоящем времени, Laravel-кабинет может разрабатываться параллельно в отдельном репозитории, но его завершение и запуск — после выпуска публичного сайта; WEB не получает backend кабинета. Готовность и тестирование Laravel не блокируют публикацию сайта; не размещать неработающую ссылку входа. Адрес страницы согласовывать в рамках обычной работы над IA. Любой содержательный PR должен фиксировать reviewed SHA, результаты и лицо, принявшее редакционное решение; технический merge или зелёный CI не считается таким решением. Защищённый план v2 не изменять ради этого дополнения.
